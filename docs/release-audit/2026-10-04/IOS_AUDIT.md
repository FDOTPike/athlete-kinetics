## Two defects in the existing iOS plan that must not be implemented literally

1. **SDNN must not be relabeled as RMSSD.** `docs/ANALYSIS_ios_biometrics_gap.md:103` maps HealthKit HeartRateVariabilitySDNN into `rmssdMs` and `ln_rmssd`. Apple's sample is the standard deviation of beat intervals, not RMSSD; the existing model/schema explicitly uses RMSSD (`aggregate.ts:40`, `003_state_vector.sql:56`). This is a P1 data-meaning hazard in a plan, not an already-running iOS bug. Preserve the metric identity and source/baseline when introducing SDNN, using an append-only schema/aggregation adaptation if needed; do not mix platforms' measurements or silently rename them. Initially ship sleep/RHR parity and honestly unavailable HRV if a correct HRV adaptation needs more work. [Apple HRV definition](https://developer.apple.com/documentation/healthkit/hkquantitytypeidentifier/heartratevariabilitysdnn?changes=_7__8).

2. **HealthKit does not reveal whether read access was denied.** The Android interface `healthConnect.ts:48` and proposed iOS interface in `ANALYSIS_ios_biometrics_gap.md:85` promise `hasGrantedPermissions(): boolean`. Native authorization-request success means the request completed, and an empty query can mean no data or no read access. Do not port Android's “ready/denied” grant detection by checking HealthKit write-authorization status or treating request success as granted reads. Adapt the UI/status semantics and tests around requested/read-availability/empty-data states while preserving explicit authorization and operation/athlete ownership. [Apple authorization](https://developer.apple.com/documentation/healthkit/authorizing-access-to-health-data?changes=_2__9&language=objc).

HealthKit sleep samples also need deduplication/interval overlap handling, waking-date/time-zone aggregation and no-data handling; iOS15.1 has fewer stage types than iOS16+, so richer stages must be availability-guarded rather than raising the whole app's minimum OS solely for those stages.
