# 06 — Validation Protocol (Prospective, Athlete-Separated, Owner-Gated)

Status: a design for a research pilot, authorized by the decision token (RESEARCH PILOT ONLY) as the only forward artifact of this discovery. It is **not** ratified for execution: running it requires the owner's separate approval, an ethics/consent review, and a domain-expert sign-off named in §11. It produces no athlete-facing behavior and holds no prescription authority — the output is knowledge, gated before it could ever become product.

**Blinding gate (added per Round 4 review — the token authorizes *blinded* validation only, and that requires stated mechanics rather than an adjective).** The following are execution preconditions, not analysis preferences:

1. **Holdout labels stay locked.** The RPE labels for every evaluation partition (Arm P holdout athletes; Arm I future-session holdouts) are sealed at partition time and are **not readable by anyone building, fitting, tuning or selecting a model**. Custody sits with someone who is not doing the modelling.
2. **The analysis is frozen before unblinding.** The pre-registration — feature sets, M0/M1 specifications, partitions, metrics, subgroup cuts and the §8 thresholds as ratified under UD-2 — is written down and version-pinned **first**. Unblinding is permitted only against a frozen analysis.
3. **The unblinding event is single, dated and authorized.** Exactly one unblinding occurs, recorded with its timestamp and the approver (the UD-1/UD-7 authority). Holdout metrics computed before that event, or any second look after a specification change, invalidate the run.
4. **A broken seal is disclosed, not absorbed.** If holdout labels are seen early, if the specification changes after unblinding, or if the analysis is re-run against the same holdout, the pilot reports itself as **exploratory** and cannot support any acceptance decision.

Nothing here loosens §11: owner approval, ethics/consent review and domain-expert sign-off remain separate and prior.

Design purpose: determine whether any individually calibrated advisory effort estimate is *measurable* in this app's population and modality — before anyone debates shipping one. The pilot is designed so that "no" is a publishable, actionable outcome.

## 0. Status, authorization, and the blinding gate

*(Section number added per Antigravity panel P2-6: `08` D-MADE-7 and other documents cite `06` §0 for the status and blinding-gate block above, which was previously an unnumbered preamble.)*

## 1. Target label and collection timing

- **Primary label:** athlete-entered set RPE (RIR-anchored 0–10) captured at set logging time in the existing flow [R03]. Rationale: it is the construct any advisory would estimate (01 §1), and it is already collected with honest null semantics.
- **Secondary labels:** estimated RIR at set end (0–5 band scale to keep the athlete away from noise-dominated high-RIR ranges [S03]); post-session session RPE ~30 min after session end per the Foster convention [S07]; optional subjective cue tags (breathing/talk/form) as separate fields, never mixed into the RPE label.
- **Barred features — explicit deny-list (added per Antigravity panel P2-11, P2-12, P2-14).** Beyond the biometric block itself, the following may never enter M0 or M1's non-biometric half, because each carries either the label or a readiness signal:
  - **`session.session_rpe`** and any aggregate derived from it — it is the arithmetic mean of that session's set RPEs [R03], so joining it leaks the label directly.
  - **`mean_velocity_ms`** and any other mechanical kinematic column — mean velocity correlates with RPE/RIR at r ≈ −0.88 [S01, S04], i.e. it is a proxy ground truth, not a workload feature.
  - **Cumulative session set count, relative set position (`set_index / total_sets`), and session duration** — `set_modifier` truncates planned sets by up to two on low-readiness days (`policyReference.ts:41-47`), so *surviving* to a high set index or a long session is itself evidence that readiness was not low. This is survivor bias with a biometric cause.
  Any feature not on the pre-registered list requires an explicit independence argument before it may be added; "it looked useful" is not one.
- **Label timing rule:** the label must be captured *before any biometric feature for that set is shown or computed* — the pilot never puts a number in front of the athlete that could anchor their report. Ordering is enforced by capture order, recorded per event.
- **Prediction target definition (pre-registered):** set-level RPE as a continuous value is the primary target. The secondary target is band classification over the **app's five owner-ratified cue bands** (5.0–6.0 / 6.5–7.0 / 7.5–8.0 / 8.5–9.0 / 9.5–10.0 per `effortCues.ts:28-34` [R05] — corrected per second audit; the first remediation wrongly described "three app cue bands"), with an optional collapsed three-band view (≤7.5 / 8–8.5 / ≥9) reported as **exploratory robustness reporting only** — it is *not* derived from, and *not* justified by, the app's five cue bands; it is a coarser re-grouping used to check whether a result survives lower resolution, and it carries no independent authority. Neither band target is justified by ML literature (the audit corrected the first freeze's "per the [S12] ceiling" justification: S12 is a two-class result at 2-minute windows and supports no per-set granularity claim, `02` §4b/§6).

## 2. Participants, separation, and the two evaluation arms (redesigned per audit)

The first freeze's single athlete-disjoint split was **incoherent**: it held every record of a test athlete out of training while also requiring per-athlete models and athlete-specific baselines — untrainable for an athlete with zero training observations. The protocol now defines **two separately labeled designs**, and every result must state which arm produced it.

- **Arm P — Population generalisation ("does this work for a new athlete?").** Train/holdout split **at the athlete level** (athlete-disjoint): every session and set from one athlete lives entirely on one side. Only athlete-agnostic models are trained here (day-scale features + movement class → next-session/set label distribution). Answers: does any population-level relationship exist at all, and is it large enough to matter? A failure here is decisive against any shipped "works out of the box" claim.
- **Arm I — Individualisation ("does calibration help a known athlete?").** **Chronological within-athlete split**: an athlete's earliest rated sessions form their calibration window; models and baselines fit **only on that window**; evaluation runs on their **later sessions only** (strict future holdout — no random shuffling within an athlete, which would leak the future into the past). Answers: does per-athlete calibration add real out-of-sample value over Arm P and over the athlete's own historical-mean baseline?
- **Tier and modality structure (both arms):** beginner (<6 months), intermediate (6 months–2 years), advanced (>2 years), mirroring the app's training-age slots; target n ≥ 20 per tier for Arm P and n ≥ 10 per tier for Arm I. **Arm I session minima are split, per Round 4 review — a single combined “≥ 10 rated sessions” target is unsafe, because calibration could consume every session an athlete has and leave nothing to evaluate on.** Pre-register **two separate per-athlete counts**: a minimum **calibration window** (candidate: ≥ 6 rated sessions) *and* a minimum **future holdout** (candidate: ≥ 4 rated sessions occurring strictly after the calibration window closes). An athlete missing **either** count is **excluded from Arm I**, and any Arm I result computed over athletes who do not meet both is reported **NOT EVALUABLE** with its counts. These are design targets for power discussion, **not validated acceptance thresholds** (final numbers belong to the owner/domain-expert gate, §11).
- **Exercise modalities (stratified, never pooled silently):** squat-pattern barbell; horizontal press; vertical press; hip hinge; bodyweight work; conditioning finishers — estimation accuracy differs by movement class and muscle mass [S03].
- **Inclusion/exclusion:** adults; no known cardiovascular, respiratory, or metabolic conditions that exercise stress could aggravate (safety screen); no medications materially affecting HR/HRV when the HRV/HR arm is analyzed; athletes under 18 excluded outright.
- **Withdrawal:** any athlete may stop at any time with data deleted on request (05 §4); withdrawal is recorded, not imputed around.

**Leakage rules for contemporaneous subjective inputs (per audit).** Any baseline or feature using **contemporaneous RIR** (the athlete's just-given "reps left" for the same set) is barred as an input to a model targeting that set's RPE — RPE is the RIR anchor on the same scale, so this is trivial leakage unless a leakage-free calibration procedure is specified and pre-registered (e.g. RIR anchors elicited on *different* movements, or a within-athlete mapping fitted on earlier sessions only and applied forward). Absent such a pre-registered procedure, contemporaneous RIR is excluded from inputs entirely. The same rule bars any feature derived from the same set's report (cue tags attached to the set being predicted).

## 3. Manual RPE/RIR reference protocol (the ground truth discipline)

- Reference = the athlete's own report, collected per §1. There is **no external physiologic ground truth for perceived effort** — the pilot validates whether biometrics can *predict the athlete's report*, not whether biometrics know "true" effort. Any writeup must say exactly this.
- Anchor training: each athlete gets one standardized orientation on the RIR-anchored scale (the app's existing cue bands [R05]) to reduce scale-usage variance; no coaching of answers afterward.
- Failure-test sets are **not** part of routine collection (safety and ecological validity); a small optional substudy may use controlled near-failure sets to calibrate the RIR anchor against reality [S03], with its own consent and supervision.

## 4. Device, source, and metadata capture

Every event row records: date; device class (phone-only / watch model / strap model if the athlete owns one); the exact record types present; vendor write timing (record timestamp vs Health Connect ingestion); sync latency; app version; movement id; set index; load/reps; rest interval preceding the set; session order within the block; and the label events with their capture order. Provenance per row is mandatory (05 §4); vendor heterogeneity [R01; `04` §3, Configuration S2] is a variable of interest, not noise to hide.

## 5. Missing-data behavior (predefined, non-negotiable)

- Missing biometric day → the set contributes label-only rows; no imputation from neighbors, population means, or the athlete's other days.
- Missing label (athlete skipped RPE) → the set contributes biometrics-only rows; **no backfilled label ever exists** [R03 law carried into research].
- Staleness: biometric records older than 30 h relative to a morning-read construct are flagged stale and analyzed separately, never silently merged.
- Missingness itself is reported: per-athlete, per-modality, per-device-class missingness rates appear in the final analysis. A pilot that hides its missingness has failed its own standard.

## 6. Counterexamples, adversarial coverage, and sensor dropout

The collection protocol *actively schedules* adversarial conditions rather than waiting to stumble into them: heavy sets with long Valsalva; small-muscle isolation vs large-muscle compounds at matched RPE; the same session repeated across readiness extremes; sessions after poor sleep vs good sleep; caffeine vs no-caffeine sessions (self-reported); hot vs temperate environments; circuit-style sessions; double sessions. Sensor dropout (dead watch, unworn strap, unsynced companion app) is recorded as a condition, not discarded. The confounder list from the WO (§4.4) is encoded as mandatory per-session annotations: exercise type/muscle mass, set duration, rest interval, breath holding, caffeine/stimulants, heat/hydration, altitude, medication, illness, anxiety, sensor fit/motion artifact, skin perfusion, device lag, individual conditioning, circuit vs heavy structure, missing/stale records.

## 7. Analysis plan (pre-registered before first data; redesigned per audit)

- **Splits:** Arm P — athlete-disjoint train/holdout, split seed recorded before analysis. Arm I — chronological within-athlete calibration window → future-session holdout (§2). Every reported number names the arm that produced it. **Preprocessing, feature scaling, and hyperparameter tuning happen inside training partitions only** (fit on train, transform/apply on holdout — no statistic computed over the full dataset leaks into evaluation).
- **The decision-critical comparison — incremental-biometric ablation (added per second audit).** Baseline comparisons alone cannot answer whether *biometrics add value*; the pilot's core analysis is a matched ablation run on **identical splits and rows**:
  - **M0 — workload/context only, every feature pinned to its AS-WRITTEN value (tightened per Reviewer B B-4):** current load relative to athlete capacity (a declared pre-pilot capacity assessment or a trailing recent-best for that movement — **subject in full to the Arm P cold-start rules below**, which bar any capacity denominator drawn from the evaluation window), reps, set index, **preceding rest interval (as-written only — see the fourth-door rule below)**, movement class.

    **Why "as-written" is load-bearing, not a formality.** In the live app the planned prescription is biometric-modulated on *three* axes, not one: `evaluatePolicy` derives `load_modifier` (0.85–1.05) from `readiness_score` and `hrv_z`, `set_modifier` (−2…+1) from `readiness_score` and `sleep_efficiency_pct`, **and** `rpe_cap` from both (`policyReference.ts:36-55`). Excluding planned target RPE therefore closes only one of three doors. If the pilot records **executed** values, then on a low-readiness day the prescribed load was scaled down and the prescribed set count truncated — so the executed load, the relative-load denominator derived from it, and the observed set-index distribution all carry readiness influence straight into the supposedly biometric-free arm.
    **Rule:** load, the relative-load numerator, reps, set index **and the preceding rest interval** enter M0 **only at their as-written (pre-modifier) values** — the programmed prescription before any readiness modifier was applied — recorded as such per row at capture time. Each must be pre-registered with the same proof demanded of any other plan-derived feature: **demonstrated independent of that day's `readiness_score`, `hrv_z` and `sleep_efficiency_pct`**. Where a pre-modifier value was not captured, the row is **ineligible for M0**, not silently back-filled from the executed value. The same pinning applies to M1's non-biometric half, so the two arms stay identical apart from the pre-registered biometric block.

    **The fourth door — preceding rest interval (added per Antigravity panel P1-3).** Three doors were closed above; a fourth was left open. In the live app the prescribed rest is a **function of the target RPE**: `restSecondsFor(rpe)` returns 240 / 180 / 120 / 90 s at RPE ≥ 9 / ≥ 8 / ≥ 7 / below (`SessionScreen.tsx:111-115`), and it is called with `safeRpe ?? currentSlot.targetRpe` (`SessionScreen.tsx:589`; the same fallback in `sessionRunner.ts:504`). Because `targetRpe` is capped by the biometric `rpe_cap`, a low-readiness day yields a lower cap and a **shorter prescribed rest**, and a high-readiness day a longer one. The athlete's executed rest is anchored to that timer. **Executed rest duration is therefore a biometric side-channel and is barred from M0 and from M1's non-biometric half.** Only the **as-written prescribed rest** — the programmed rest for that slot before any readiness modifier — may enter, pre-registered and demonstrated independent of `readiness_score`, `hrv_z` and `sleep_efficiency_pct`. Where the as-written value was not captured, the field is **missing** and the row is ineligible for M0; it is never back-filled from the executed timer. **Planned target RPE is deliberately EXCLUDED from M0 — corrected per Round 4 review, and this correction is decision-critical.** In the live app the planned prescription is **biometric-derived**: `evaluatePolicy` reads `hrv_z` and `sleep_efficiency_pct` and returns an `rpe_cap` alongside the load and set modifiers (`policyReference.ts:31-32,49,71` [R07], `05` §0). Admitting planned target RPE into the "no biometric input" arm would therefore smuggle HRV and sleep into M0 through the back door, shrink the measured M1−M0 delta toward zero, and make a null result uninterpretable — the ablation would no longer be an ablation. **No feature derived from, or modulated by, any biometric signal may enter M0.** If a plan-derived quantity is wanted as a feature, it must be a **biometric-free** one (e.g. the programmed load or rep target as written before any readiness modifier was applied), recorded pre-registered as such and demonstrated to be independent of that day's `readiness_score`, `hrv_z` and `sleep_efficiency_pct`. The same exclusion applies to M1's non-biometric half, so the two arms stay identical apart from the pre-registered biometric block. **Independent motivation (added per Round 4, scoped exactly):** [S30] reported that these same workload/context variables — relative intensity, set number and repetition number — were **associated** with set RPE across 104 subjects over eight weeks with no biometric input, and that RPE differed significantly *between exercises at the same prescribed %1RM*. That second result is the direct argument for keeping **movement class** in M0: relative load alone is not sufficient. **Bound:** [S30] fitted population-level GEE **association** models and evaluated no out-of-sample prediction, so it makes M0 an *evidence-motivated* baseline — **not** a validated one. M0's own predictive performance is established here, by the Arm P (athlete-disjoint) and Arm I (chronological within-athlete) evaluations, and nowhere else.
  - **M1 — M0 + biometric features:** the identical model specification plus **only pre-registered biometric features**: prior-night HRV z and prior-night sleep efficiency. **No other feature may differ between M0 and M1** — same specification, same preprocessing, same tuning budget (corrected per third audit; the earlier "any session-context features the ratification permits" wording is withdrawn because it would confound the Δ).
  - **Paired comparison population (defined exactly; per Round 3 closure).** The incremental delta is only interpretable on a matched population, so:
    1. **Identify** the **biometric-eligible** rows — those carrying the *complete* set of pre-registered biometric inputs M1 requires (prior-night HRV z **and** prior-night sleep efficiency). A row missing either is not eligible.
    2. **Fit and evaluate M0 and M1 on exactly those same rows and exactly the same splits.** The M1−M0 delta is read from this paired fit and from nothing else. M0 is *re-fit* on the eligible subset for this purpose — a delta against an M0 fitted on a different row population is not an ablation.
    3. **Separately, evaluate M0 over the full labelled population** as the **coverage reference** — the honest picture of what a non-biometric model achieves for everyone, including athletes who would never be eligible for M1. This number is reported alongside the delta and never subtracted from it.
    4. **Report** biometric-eligible rows / all labelled rows (per athlete, per tier, per arm), the **missingness pattern** behind ineligibility, and any **selection differences** between the eligible subset and the full population (tier mix, device class, movement class, session type, RPE distribution). If the eligible subset is systematically easier or systematically fitter than the full population, the delta is a selected-sample result and must be labelled as one. A large Δ on a 20% coverage subset is not a product claim.
  - **Arm P cold-start behaviour (defined exactly; per Round 3 closure).** Arm P predicts for an athlete the model has never seen, so every input must be constructible at that moment:
    - **Strict information boundary.** Relative-load / capacity inputs may be computed **only from information available before the predicted set**. No future set, no holdout label, and no full-dataset statistic may enter them — including "the athlete's heaviest recorded set" when that maximum is drawn from the evaluation window.
    - **Two distinct legitimate sources, never conflated.** (a) A **declared pre-pilot capacity assessment** — a 1RM, e-1RM, or rep-max recorded at enrolment, before any predicted set exists; this is available on set one and is the genuine cold-start source. (b) **Trailing historical load** — a running maximum or recent-best accumulated from the athlete's own already-observed sets inside the pilot; this is unavailable at enrolment and becomes available only as the athlete accrues history. **Denominator purity rule (added per Antigravity panel P1-4):** pinning the relative-load *numerator* is not sufficient, because the *denominator* built from source (b) is itself contaminated — sets executed inside the pilot were lifted under `load_modifier` (0.85–1.05, `policyReference.ts:35-40`), so a run of low-readiness days depresses the trailing best and silently inflates today's relative load. When source (b) is used, the trailing capacity must be computed **exclusively from as-written (pre-modifier) prescribed loads**, never from executed loads; if as-written history is unavailable, M0 capacity is restricted to source (a), the pre-pilot assessment. Each row records **which** source produced its capacity denominator, and the two are never averaged into one undifferentiated feature.
    - **If neither exists,** the capacity field is **missing** — encoded with a missing-indicator per §5 — or the prediction comes from a **pre-registered cold-start alternative** (e.g. a movement-class model using planned target load only), named in the pre-registration before first data. Silently back-filling from later observations is the failure this rule exists to prevent.
  - **Biometric run-in for Arm P holdout athletes (added per Antigravity panel P2-10).** HRV z is z-scored against a 28-day baseline [R01b]. A holdout athlete enrolled at pilot start has no such history, so on a standard four-week pilot **every one of their sets would be M1-ineligible** and the incremental comparison would evaluate on an empty or badly truncated population. Pre-register a mandatory **14–28 day biometric run-in before an Arm P holdout athlete's first predicted set**, with the run-in window excluded from evaluation; where the run-in is incomplete, HRV z stays missing per the rule below and the coverage report must state how many holdout athletes were affected.

  **HRV z-score normalization (per Round 3 closure).** An athlete's HRV z may be computed **only from that athlete's biometric history available before the prediction**. It may not use future observations and may not use RPE labels in any form. Where the pre-registered minimum baseline history does not yet exist, HRV z **stays missing** (missing-indicator per §5) rather than being approximated from a population statistic, a truncated window, or any window overlapping the evaluation rows. The same information boundary applies inside Arm I's calibration-window design.
  - **Report:** the out-of-sample Δ between M1 and M0 (ΔMAE on continuous RPE; Δ high-effort miss rate; Δ band accuracy for the secondary target) with bootstrap confidence intervals, **per arm** (Arm P: athlete-disjoint; Arm I: chronological within-athlete), plus the coverage rates above.
  - **Decision reading:** M1 must beat M0 out-of-sample on matched biometric-eligible rows — not merely beat naive baselines — for any biometric advisory to be justified, with the coverage caveat attached. [S28] found exactly this HRV increment in lab conditions (flywheel squat, chest ECG); the pilot tests whether it survives field conditions and consumer data. **Sharpened per Round 4:** the comparison is explicitly incremental over an *evidence-motivated* baseline — [S30] found workload/context variables associated with set RPE at population scale without biometrics (association only; no out-of-sample prediction was evaluated there). A small M1−M0 delta is therefore a genuine null result about biometrics **provided M0's own measured performance in this pilot is non-trivial**; if M0 also performs poorly here, the correct reading is that neither arm has been shown to work, not that biometrics were tested and failed. Report M0's absolute performance beside every delta so the two cases stay distinguishable. [S29] separately removes the sensor-accuracy escape hatch at discrete timepoints (consumer-watch HR agreed with ECG around resistance sets), while leaving continuous intra-set capture, cross-device equivalence and Health Connect delivery unvalidated — so a null delta cannot be explained away as "the watch could not measure it" without naming which of those unvalidated conditions is responsible.
- **Naive reference baselines (reported alongside, never a substitute for the ablation):** (a) population mean RPE per movement class (Arm P); (b) planned target RPE as naive predictor (both arms) — **flagged per Round 4 review as a biometric-contaminated reference**, since the live planned RPE cap is modulated by `hrv_z` and `sleep_efficiency_pct` [R07]; it is reported as a practical yardstick only and must never be described as a non-biometric baseline or substituted for M0; (c) athlete's own historical mean RPE per movement, fitted on the calibration window only (Arm I — by construction unavailable in Arm P); (d) contemporaneous-RIR models only under a pre-registered leakage-free calibration procedure (§2 leakage rules), otherwise excluded.
- **Per-athlete estimation must be regularized (added per Antigravity panel P2-13).** Arm I fits per-athlete calibration parameters from a calibration window of candidate ≥ 6 sessions spread over six movement classes. Unconstrained per-athlete-per-movement dummy coefficients are **rank-deficient at that volume** — some cells will have one observation or none. Pre-register **hierarchical shrinkage** (ridge / partial pooling toward the population coefficient) rather than free per-cell estimation, and report the shrinkage parameter with the results.
- **Model classes:** the M0/M1 ablation uses athlete-agnostic regularized regression (Arm P) and the same specification with per-athlete calibration parameters fitted on the calibration window only (Arm I) — the only class consistent with the app's closed-form deterministic posture [R01b] and the pilot's data density; any complex model is exploratory-only and reported as such.
- **Metrics (per arm; per athlete and pooled):** MAE and bias on continuous set RPE; band confusion for the secondary five-band target; calibration (predicted vs observed frequencies); high-effort miss rate (fraction of athlete-reported ≥9 sets predicted below 8 — the false-reassurance direction); false-reassurance rate at ≥8.5; uncertainty-interval coverage; and the M1−M0 deltas above.
- **Subgroup reporting:** per tier, per movement class, per device class, per session type (strength/hypertrophy/conditioning/bodyweight). Pooled-only results are explicitly disallowed in the final report. **Clarified per Antigravity panel P1-6:** this bars *reporting only the pooled number*; it does **not** require every subgroup to clear an acceptance gate. Subgroup cells are **descriptive** (point estimate + exact binomial interval + raw counts + MAE) and are read for harmful-direction signal; the acceptance gate itself is evaluated at the arm level, and at tier level where powered (§8). A subgroup below its reporting floor is disclosed as NOT EVALUABLE with its counts and does **not** block the arm-level decision.
- **Uncertainty and bias reporting:** Arm I per-athlete intervals via bootstrap over that athlete's holdout sessions; Arm P intervals via bootstrap over holdout athletes; any pooled number additionally reports its athlete-count basis. Missingness rates travel with every table (§5).

## 8. Candidate thresholds — explicitly NOT decided here

The WO forbids inventing acceptance thresholds; this protocol proposes *candidate* thresholds for the owner/domain-expert gate to adopt, reject, or move, each with its rationale and its evaluation arm: within-athlete set-RPE MAE ≤ 0.5 in **Arm I** (rationale: it sits below the ~1-repetition perceptual noise floor near failure [S03], and it is the neighborhood of the MAE ≈ 0.62 RPE achieved only by an instrumented robotic load cell [S27] — a consumer-biometric path must approach an honestly calibrated bar or not exist); high-effort miss rate ≤ 10% in either arm (false-reassurance guard) — **with a pre-registered evaluability floor, added per Round 4 review: this rate is a ratio whose denominator is athlete-reported ≥9 sets, which are not routinely collected, so an arm or subgroup could otherwise "pass" on zero or a handful of qualifying labels.** **Corrected per Antigravity panel P1-5 and P1-6 — the previous formulation was mathematically unsatisfiable and structurally deadlocked, and is withdrawn.** It paired a ≤10% gate judged on a **95% CI upper bound** with denominators of ≥30 (arm) and ≥15 (subgroup). Those cannot coexist: by the rule of three, an upper bound of 3/N with **zero** misses is 20% at N = 15 and exactly 10% at N = 30 — so a subgroup could never pass at any miss count, and an arm could pass only with a perfect zero-miss record. Separately, requiring ≥15 athlete-reported ≥9 sets *per movement-class subgroup* is unreachable at the planned Arm I volume (≈40–60 such sets per tier spread over six movement classes), which — combined with §7's ban on pooled-only reporting — would render every subgroup NOT EVALUABLE and leave the arm unable to reach any decision at all.

  The gate is therefore restated at two levels:
  - **Decision level (arm, and tier where powered): the ≤10% high-effort miss rate is the acceptance gate**, judged on the **upper bound of a bootstrap 95% CI**, and evaluable only at a pre-registered denominator large enough for that bound to be attainable — candidate **≥ 75** athlete-reported ≥9 sets, which admits a non-zero miss count rather than demanding perfection. Below that denominator the arm's gate is **NOT EVALUABLE**, reported with raw counts, and cannot support acceptance.
  - **Subgroup level (movement class, device class, session type): descriptive only.** Report the **point estimate with its exact binomial interval and raw counts**, plus continuous MAE, at a floor of **≥ 10** qualifying sets. Subgroups are read for **harmful-direction signal**, not gated on ≤10%, and a subgroup below the floor is reported as NOT EVALUABLE **without blocking the arm-level decision**.
  Final denominators, like the thresholds themselves, are **owner/domain-expert decisions under UD-2** — the candidates above are unratified; secondary-band classification materially above the applicable §7 baselines **within the same arm**; no athlete subgroup with bias direction harmful (under-predicting effort). **Corrected per audit, restated exactly per Round 3 closure:** the first freeze justified band granularity as "the [S12] ceiling" — S12 is a two-class result and supports no per-set granularity claim, so that justification is withdrawn. The accurate position: **the app has five cue bands** (`effortCues.ts:28-34` [R05]), and the secondary band target is defined on those five bands together with [S03]'s perceptual-noise argument. The **optional collapsed three-band view is exploratory robustness reporting** — a coarser re-grouping reported to test whether a result survives lower resolution. It is **not derived from, and not justified by, the app's five cue bands**, and no acceptance decision may rest on it. **These are unratified placeholders.** The stop rule: if candidate thresholds are not met on the respective arm holdouts with pre-registered analysis, the advisory option dies and the pilot's honest output is "not measurable." **Execution gate (unchanged and restated per Round 3 closure): pilot execution is NO-GO.** Nothing in this protocol may be run until **UD-1** (ratify the protocol), **UD-2** (adopt or move these thresholds), and **UD-7** (data governance, retention, consent text, and IRB/EC approval) are each resolved, together with the qualified approvals in §11. Thresholds remain explicitly **unratified** until UD-2 closes.

## 9. Opt-out, manual-only path, and data handling

- Participation is opt-in; the app (or pilot build) functions identically without it. Every participant keeps the manual-only path forever (05 §10).
- Pilot data lives in the same local-first posture: on-device capture, exported only with explicit per-export consent, de-identified at export (athlete codes, no free-text), held by the owner under a stated retention limit, deleted on request. No third-party transfer. No device-extracted raw streams beyond the app's existing compacted daily types [R01].
- The pilot never modifies the athlete's plan, prescriptions, or progression behavior — its presence in a training block is observational only. Any observed interaction with training behavior is reported, not designed.

## 10. Safety monitoring

- Stop criteria for the pilot itself: any adverse event plausibly linked to participation; any indication the data is being interpreted as medical (05 §7); any privacy incident. The pilot pauses and the owner re-ratifies or kills it.
- The failure-test substudy (if run) requires direct supervision and its own consent language; it never runs inside the pilot's routine capture.

## 12. What this protocol deliberately does not do

It does not estimate RPE for anyone. It does not put biometrics in front of athletes during sessions (the label-anchoring rule, §1). It does not touch prescription state [R01, R01b]. It does not collect SpO2 [05 §8]. It does not validate "biometric RPE" as a concept — it tests whether one specific, individually calibrated, day-scale-feature advisory is measurable against athlete-reported labels, and it is built so the answer can be no.
